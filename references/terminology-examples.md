## 生成、存储与记录

### 物化（materialize）

“物化视图（Materialized View）”是数据库术语，表示将查询结果存储下来供后续读取，保留其专业名称。参见 [PostgreSQL 物化视图文档](https://www.postgresql.org/docs/18/rules-materializedviews.html)。

文件生成场景直接说明生成、渲染或写入哪个文件。完成状态依据实际写入结果表述。

| 原表述 | 已有语境 | 建议表述 |
| --- | --- | --- |
| 物化这个视图。 | 数据库操作是创建物化视图 | 创建物化视图。 |
| 接下来物化 `.env`。 | 根据模板生成配置文件，操作待执行 | 接下来根据模板生成并写入 `.env` 文件。 |
| `.env` 已物化。 | 文件写入成功，已生成目标文件 | 已生成 `.env` 文件。 |

### 台账（ledger）

账本或历史操作记录有明确用途时，按业务含义描述。SQL Server Ledger 是提供历史记录与篡改检测能力的正式数据库功能，保留功能名称。参见 [Microsoft Ledger 概述](https://learn.microsoft.com/en-us/sql/relational-databases/security/ledger/ledger-overview?view=sql-server-ver17)。

普通数据结构写明实际类型、记录内容或用途，例如内存字典、任务状态表、操作历史记录。

| 原表述 | 已有语境 | 建议表述 |
| --- | --- | --- |
| 把请求状态写进台账。 | 内存字典保存请求的当前状态 | 将请求状态写入内存字典。 |
| 用台账追踪修改。 | 保存每次修改的历史，供审计查询 | 记录每次修改，供后续审计查询。 |
| 数据库用了 Ledger。 | 已启用 SQL Server Ledger 功能 | 数据库已启用 SQL Server Ledger。 |

### 对账（reconciliation）

财务对账指核对账目或交易记录，按业务含义保留。其他记录核对场景写清核对双方和目标；数据结构测试则写明校验字段、检查格式、比较预期结果等实际行为。

| 原表述 | 已有语境 | 建议表述 |
| --- | --- | --- |
| 对账一下返回结构。 | 校验 API 响应字段是否符合约定 | 校验 API 响应字段是否符合约定。 |
| 对账发现差异。 | 核对支付记录与银行流水 | 核对支付记录与银行流水时发现差异。 |

## 验证与修复

### 绿

CI 的绿色状态通常表示相应检查通过。技术回答应写明实际执行的检查及其结果，执行范围按记录表述。代码改动和验证结果分别描述。

| 原表述 | 已有语境 | 建议表述 |
| --- | --- | --- |
| CI 全绿了。 | CI 工作流已执行，全部检查通过 | CI 检查全部通过。 |
| 已经绿了。 | 实际只执行了语法检查，检查通过 | 语法检查通过。 |
| 本地全绿。 | 本地执行 `npm test` 并通过 | `npm test` 通过。 |
| 代码绿了。 | 仅完成代码改动，测试待执行 | 代码改动已完成，测试待执行。 |

### 止血

用实际故障、具体修复动作和处理结果说明工作。紧急程度与修复成本依据实际影响和分析表述。临时处理写明采取的措施及当前修复状态，直接修复写明修正的错误。

| 原表述 | 已有语境 | 建议表述 |
| --- | --- | --- |
| 这个问题已经止血。 | 只增加异常捕获并忽略异常，触发异常的逻辑仍待修复 | 已增加异常捕获并忽略该异常。触发异常的逻辑仍待修复。 |
| 先止血再说。 | 线上出现故障，已决定先回滚本次发布，再修复故障 | 先回滚本次发布以恢复服务，再修复导致故障的改动。 |
| 给字段映射止血。 | 已确定修复动作是修改错误的字段映射 | 修正字段映射错误。 |

## 界面、资源与集成

### 读作（read as）

视觉描述中的 read as 表示某个元素被理解为另一种元素。改写时优先记录可见性、边界、对比度、点击区域等具体观察；对用户理解的描述以实际反馈或可用性测试为依据。

| 原表述 | 已有语境 | 建议表述 |
| --- | --- | --- |
| 用户把按钮读作图片。 | 用户的实际反馈是按钮难以识别 | 用户反馈按钮难以识别。 |
| 按钮读作图片，得补点高光。 | 已观察到按钮边界不清晰，计划增加高光 | 按钮边界不清晰。计划增加高光以突出按钮。 |

### 猪（hog）

资源描述中的“猪”源于 hog，表示资源占用过多的实体。根据实际对象写明进程、容器或服务，并说明占用的资源，例如 CPU、内存或带宽。

| 原表述 | 已有语境 | 建议表述 |
| --- | --- | --- |
| 这个容器是内存猪。 | 已观察到该容器内存占用较高 | 该容器的内存占用较高。 |

### 夹具（fixture）

手写输入数据写为“测试数据”或“预设测试数据”。涉及环境准备、初始化等内容时，按实际用途描述。`pytest.fixture` 等 API 名称保留原样。

| 原表述 | 已有语境 | 建议表述 |
| --- | --- | --- |
| 加一组夹具。 | 为测试准备手写输入数据 | 添加一组预设测试数据。 |
| 把 fixture 接进测试。 | 测试需要使用 `pytest.fixture` 定义的初始化函数 | 在测试中使用 `pytest.fixture` 定义的初始化函数。 |

### 接线（wire）

软件开发中的 wire 可能表示连接模块、注册回调、配置依赖或绑定事件。直接写明连接双方和实际动作；硬件接线按其专业含义表述。

| 接线完成。 | 已将保存按钮的点击事件绑定到保存函数 | 已将保存按钮的点击事件绑定到保存函数。 |

| 原表述 | 已有语境 | 建议表述 |

## 流程条件与功能开关

### 门控（gate / gating）

根据实际机制选择表述：

- 流程中的 Quality Gate：写清进入下一阶段前必须通过的检查或满足的条件。
- 流程中的 Confirmation Gate：写清需要由谁确认的具体事项。
- 代码中的 Feature Gate：写为“功能开关”或“配置开关”，说明其控制的功能。

专业领域已有的“门控”术语按其专业含义使用。
